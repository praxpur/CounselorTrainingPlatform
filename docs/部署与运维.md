# 部署与运维

当前学校服务器、域名尚未申请，交付代码、Linux 模板和本地维护验证；本文件不是已完成生产部署的记录。
部署前先确认目标系统、域名/证书、微信接口权限、数据保留规则和运维负责人。正式接口不要使用测试登录。

## 目录与运行方式

模板采用单个 Node API 进程，监听 `127.0.0.1:3000`，Nginx 提供 HTTPS。禁止使用 PM2 Cluster、Node Cluster 或多个 API 实例并行争写同一个库。
备份、清理、名单导入是短期维护连接，不是第二个 API 服务实例。

| 位置 | 用途 | 权限 |
|---|---|---|
| `/opt/counselor/releases/<版本>` | 经测试的发布版本 | root 管理，应用只读 |
| `/opt/counselor/current` | 当前版本软链接 | root 管理 |
| `/etc/counselor/training.env` | 运行配置 | root:counselor，0640 |
| `/var/lib/counselor/training.db` | SQLite 数据库及 WAL | counselor，目录 0700 |
| `/var/lib/counselor/uploads` | 私有证明材料 | counselor，目录 0700 |
| `/var/backups/counselor` | 数据库与材料完整备份包 | counselor，目录 0700 |

使用仍受支持的 Node LTS，最低 **22.16.0**。`node:sqlite.backup()` 在该版本加入，维护脚本会明确拒绝缺少该 API 的运行时，不能以复制活动 `.db` 单文件替代在线备份。[Node SQLite 文档](https://nodejs.org/api/sqlite.html#sqlitebackupsource-db-path-options)
确认 `/usr/bin/node` 实际版本；若 Node 安装在其他位置，同步修改所有 unit 和脚本中的路径。

在代码目录中执行 `cd server && npm ci --omit=dev`。发布应基于经验证并提交的版本，不要把开发数据库、密码名单、`tmp`、`node_modules` 工作副本或材料目录随手打包上传。
数据与备份目录必须位于代码目录之外。升级代码不删除数据；涉及 schema 迁移时先备份并做恢复演练。

## 初始化与配置

下列命令是目标 Linux 主机上的安装示例，须先填写真实版本与域名；本次没有执行：

```sh
sudo useradd --system --home /var/lib/counselor --shell /usr/sbin/nologin counselor
sudo install -d -o counselor -g counselor -m 0700 /var/lib/counselor /var/backups/counselor
sudo install -d -o root -g counselor -m 0750 /etc/counselor
sudo install -o root -g counselor -m 0640 deploy/training.env.example /etc/counselor/training.env
```

将 `current` 指向实际发布版本后，核对环境文件中的绝对路径。修改数据位置时同步修改 systemd 的 `ReadWritePaths`，Nginx 上游端口也要与 `PORT` 一致。
正式环境必须为 `NODE_ENV=production`、`ENABLE_DEV_LOGIN=0`；运行预检：

```sh
sudo -u counselor sh -c 'set -a; . /etc/counselor/training.env; set +a; exec /usr/bin/node /opt/counselor/current/deploy/check-runtime.js'
```

预检拒绝旧 Node、开发登录、公网后端监听、内存数据库或代码目录内的数据路径。
路径检查会解析已存在父目录的软链接/junction，再附加尚未创建的后缀；通过 `current` 等别名指向代码目录的数据路径同样被拒绝，无法解析的链接也不会被放行。
按[账号与名单导入](账号与名单导入.md)在受保护文件中准备首个管理员，再使用相同环境执行 `server/manage-users.js bootstrap <私有JSON路径>`。不要将真实初始密码放入命令行、Git、小程序包或公开备份；使用学校认可的渠道单独发放。

## HTTPS 代理与微信域名

提供的文件：

- `deploy/nginx/counselor.conf` → `/etc/nginx/conf.d/counselor.conf`，位于 `http` 上下文。
- `deploy/nginx/counselor-proxy.conf` → `/etc/nginx/snippets/counselor-proxy.conf`。
- `deploy/nginx/nginx.conf.example` 为独立主机全局示例；已有其他站点时只合并设置，不能直接覆盖现有主配置。

替换全部 `training.example.edu.cn`，填入学校真实证书和私钥路径，私钥只允许服务器管理员读取。模板使用 TLS 1.2/1.3，HTTP 固定跳转到配置的 HTTPS 域名。
一般 JSON 请求上限 16 KiB，`/api/proofs` 上传上限 5 MiB；测试登录路径在代理层直接 404。
代理不公开代码、数据库或材料静态目录，所有材料下载仍由应用鉴权。请求及响应不作完整缓冲，使后端上传拒绝和下载背压能及时生效。[Nginx 代理文档](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_request_buffering)

限流模板为每源 IP 200 请求/秒、突发 2000；登录为 30 请求/秒、突发 500；并发连接上限 2000。
这是兼顾校园 NAT 下 500 人突发的起始配置，不是验收结果。后端仍独立限制登录尝试、密码哈希、上传和导出并发，可能返回 429；压测不能把预期的 409 满员与网络错误混算。[Nginx 限流文档](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html)
若还有校级负载均衡/CDN，只向确切可信的代理配置真实 IP，不信任任意客户端转发头。
应用当前只使用 TCP 对端作为接口内 IP 限制的来源，经过本模板代理后该来源是 `127.0.0.1`，因此后端 IP 窗口由全部用户共享；网络层的逐客户端限流由 Nginx 负责。登录并发和首次改密须单独验收，不能从已建立会话的业务压测结果推断。

访问日志仅记录方法和路径，不记录请求体、Authorization 或查询串；`edge` 是代理请求编号，`app` 是应用返回的 `X-Request-Id`，可关联业务审计。按学校规定配置日志轮换、保留和访问权限，并监控磁盘空间。
防火墙只放行学校批准的管理入口和 80/443，不向公网开放 3000。

目标主机完成证书安装后再验证并启动：

```sh
sudo nginx -t
sudo systemd-analyze verify deploy/systemd/counselor.service deploy/systemd/counselor-backup.service deploy/systemd/counselor-cleanup.service deploy/systemd/counselor-backup.timer deploy/systemd/counselor-cleanup.timer
sudo install -m 0644 deploy/systemd/counselor.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now counselor.service
curl --fail http://127.0.0.1:3000/health
curl --fail https://实际学校域名/health
sudo journalctl -u counselor.service --since today
```

在发布小程序前，在项目根目录显式运行：

```sh
node scripts/configure-api.js https://实际学校域名
git diff -- utils/store.js
```

脚本只精确修改 `const API_BASE`，生产仅允许不含凭据、路径、查询的 HTTPS 443 地址；内网调试须显式 `--dev`，不会自动更改当前局域网地址。
在微信公众平台配置同一 HTTPS 域名的 request、downloadFile 合法域名，完成位置接口申请和隐私说明，然后真机验证登录、证明材料下载、扫码/定位和 Excel 预览。

## 一致备份与校验

使用相同环境执行，或安装提供的 backup unit：

```sh
node server/maintenance.js backup /var/backups/counselor
node server/maintenance.js verify /var/backups/counselor/实际备份目录
```

`backup` 使用单独只读连接做 SQLite 在线备份，**不会先加载应用并迁移源库**。源库可保持 WAL 模式和在线服务。
随后读取快照中的材料清单，只复制该快照引用的随机编号文件，保存文件大小与 SHA-256、数据库 SHA-256。完成数据库完整性、外键和全部材料校验后才把 `.partial-*` 目录发布为完整备份。
数据库清单中有缺失或大小不一致的源材料时，备份失败，不会把不完整包标成成功。
材料编号写入后不可修改；清理与备份共享维护锁，避免快照材料在复制期间被清掉。应限制文件系统访问，不手工覆盖现有编号的文件。

备份包含用户信息、凭据哈希、会话哈希和证明文件，必须保持私有权限，并按学校方案加密存储、异地复制和归档。本工具不自动删除历史备份或已提交材料；先确认保留策略与容量监控，再启用每日任务。
定期从已复制到异地的备份执行 `verify` 和恢复演练，仅“备份命令成功”不等同于已经验证可恢复。

## 恢复演练与正式恢复

恢复只写入**全新的数据库文件和材料目录**，已存在的目标会被拒绝，不能覆盖在线数据：

```sh
node server/maintenance.js restore /var/backups/counselor/实际备份目录 /var/lib/counselor/drill-20261115/training.db /var/lib/counselor/drill-20261115/uploads
```

恢复前校验整包；材料逐份复制校验，数据库通过 SQLite 备份 API 恢复并检查完整性、外键与材料清单，最后排他创建数据库目标。
演练使用隔离目录与测试服务端口，禁止误连正式小程序或把测试库替换正式库。
正式恢复须先停止 API、backup/cleanup timer 和所有维护/名单导入进程，将原数据库目录（含 WAL/SHM）及材料整体保留为回退副本；由运维明确准备新的空目标，再执行恢复、重新核对环境路径与 systemd 写权限、启动单实例并验证数据。
有 schema 迁移时不能只回滚代码，应按对应版本恢复数据与材料。恢复目标应使用支持排他硬链接的本地文件系统；失败时原备份不会被修改。

## 维护清理与中断处理

```sh
node server/maintenance.js cleanup
```

写维护才初始化应用，注册审计函数与当前 schema。它只删除过期会话，以及严格超过 7 天、没有绑定任何培训记录且 `ever_submitted=0`（从未提交过）的材料；不删除审计、曾提交证明或业务历史。
证明一旦提交，即使驳回重提时从当前记录移除，`ever_submitted` 仍保留为 1，自动清理不会删除。旧 schema 没有该字段时，维护脚本保守跳过所有有元数据材料的自动清理，并返回 `metadataCleanupSkipped=true`；只有真正没有元数据的过期物理孤儿仍可清理。
因进程中断而没有元数据的随机编号材料，仅在文件超过 7 天后清理；未知文件名和目录不删除。
材料先移到私有隔离区，在写事务内删除元数据，失败则恢复文件。进程中断留下的隔离文件在下次 cleanup 时按数据库是否仍引用来恢复或删除；隔离区未恢复前 backup 会明确拒绝。
清理按小批次持有 SQLite 写锁，仍可能短暂影响写请求，应安排在低峰期并观察 API 延迟，不把它描述成零影响维护。

维护锁为 `<DB_PATH>.maintenance-lock`，包含进程 PID 和开始时间。程序不按时间自动抢占锁。
若维护被操作系统强制终止，先查看 `owner.json` 并核实原进程确已退出，再由运维清除该锁中的 owner 文件与空锁目录，运行 cleanup 完成隔离恢复，然后重试 backup。
`.partial-*` 目录不能当作可用备份，确认无存活任务后再按明确目录处理。不要泛用递归删除整个数据或备份目录。

## 定时任务与验收边界

完成一次手动备份、校验和独立恢复演练后，再安装 `deploy/systemd/counselor-{backup,cleanup}.{service,timer}`。
时间采用 Asia/Shanghai：备份每天 02:30、清理每天 04:30，各增加最多 10 分钟随机延迟；互相碰撞会因维护锁失败，而不会并发删除文件。
可用 `systemctl list-timers`、`journalctl -u counselor-backup.service`、`journalctl -u counselor-cleanup.service` 和 `systemctl --failed` 检查运行结果；备份/清理失败、磁盘余量、证书到期都需纳入学校运维监控。

本地已验证：在线 WAL 备份期间的其他连接提交、快照材料一致性、完整性/外键/哈希检查、损坏包拒绝、全新目录恢复、维护互斥、清理回滚/中断恢复、仅删除符合条件的材料、API 地址精确替换和生产配置预检。
当前 Windows 会话 PATH 中未检测到 nginx、systemd-analyze、WSL 或 Docker，Linux 配置只作静态核对；未执行 `nginx -t`、systemd 启动、实际证书/域名或真实 500 人网络验收。
服务器申请完成后，应在真实 HTTPS 入口执行功能与 500 人负载验收，记录响应率、预期业务状态、P50/P95/P99、写入一致性，并实际完成一轮备份恢复演练。
