## A1 · P1：反向代理后，全站登录限额可被无效请求耗尽

位置：`server/auth.js:40-46,62-67`、`server/server.js:280`、`deploy/nginx/counselor-proxy.conf`。

后端用 TCP 对端地址计登录 IP 窗口，而模板所有请求都经 `127.0.0.1` 的 Nginx 上游进入。登录先累计 IP 次数，再检查账号和密码；即使请求缺少工号/密码、账号桶已经返回 429，IP 桶仍会累加。

因此按当前模板上线后，一个来源可以通过无效登录请求耗尽全校共享的 3000 次/15 分钟窗口，随后其他用户即使输入正确密码也得到 429。网络层的每客户端限流没有解决应用层把所有客户端合为一个 IP 的问题。

隔离内存工厂复现：同一代理地址提交 3000 次空对象后，合法账号经同一地址为 429，经另一 TCP 地址为 200：

```json
{"invalidAttempts":3000,"validAccountViaSharedProxy":429,"validAccountViaOtherPeer":200}
```

验证范围：计数与合法账号阻断已实测；真实 Nginx 链路未部署，跨客户端共享的可达性来自当前代理配置与代码。不是在实际学校服务上发送攻击请求。

建议：只对明确可信代理采用由代理覆盖的真实客户端地址，或明确拆分代理全局保护与用户/IP限流。不能无条件相信客户端任意 `X-Forwarded-For`。同时明确无效格式、成功登录和失败尝试的计数政策。

## A2 · P2：部分写请求在取得写锁后没有重新核验权限

位置：`server/roster.js:28-41,50-58`，`server/server.js:786-794`。

名单导入、重置他人密码在 `authorize()` 后才执行 `BEGIN IMMEDIATE`。活动发布则在读完请求体、完成鉴权后执行可能等待写锁的 INSERT。另一连接可以在等待期间撤销管理员会话，但旧请求拿到锁后仍继续写。

真实 WAL 双连接复现：管理员被运维连接重置并删除会话后，旧请求仍成功导入或改写他人密码。真实 HTTP 生产模式复现还确认活动发布返回 201，此时管理员会话已是零：

```json
{"mode":"reset","outcome":"succeeded","authorizationCalls":1,"actorSessions":0,"victimHashChanged":true}
{"mode":"import","outcome":"succeeded","authorizationCalls":1,"actorSessions":0,"newUserExists":true}
{"httpStatus":201,"actorSessions":0,"createdActivities":1}
```

前提是另一写连接在锁等待期间撤权，例如受支持的运维密码重置；不是一个没有任何权限的账号直接访问管理接口。已有登录/改密和报名模块做了锁内复核，这些写入口遗漏了同样边界。

建议：在业务写事务内取得锁后重新核验当前会话、角色和目标用户权限；不要把检查与实际写入分隔在锁等待两侧。离线运维工具应保留其独立授权语义。

## A3 · P2：备份校验未覆盖额外 WAL，恢复的可能不是已校验内容

位置：`server/maintenance.js:75-80,155-161`。

校验只计算备份 `training.db` 主文件的哈希，但 SQLite 只读连接仍可能应用旁边未纳入清单的 `training.db-wal`。恢复又重新打开同一数据库做在线复制，只查完整性和材料清单，未确保消费的是主文件哈希所代表的封闭快照。

隔离实测：正常备份产生后，在备份库连接中修改示例角色且保持 WAL 未 checkpoint。主文件 SHA 不变、校验接受，恢复后角色却为 WAL 中的新值：

```text
mainFileUnchanged: true
verifyAccepted: true
restoredRole: admin（原快照为 counselor）
```

前提是备份目录被工具打开写入、被并入额外 WAL 或发生其他备份包内容变化。**这不是远程 API 越权，也不是 SHA-256 被破解**，而是校验范围与 SQLite 实际读取范围不同。

建议：备份包校验/恢复拒绝非空 WAL、journal 等逻辑边车，或使用明确不可变的已校验副本；恢复应读取同一份被验证的快照。生产源库在线备份时读取正常 WAL 是必要功能，不应把源库与备份包混为一谈。

## A4 · P2：活动改期后，旧签退码仍能在新开始时间前签退

位置：`server/server.js:814-835`、`server/attendance.js:44-59,76-84`。

正常 HTTP 流程可触发：活动开始 → 用户签到 → 管理员开放签退 → 尚未确认参加时将活动推迟一小时 → 用户提交旧签退码。编辑成功，但旧窗口没有失效，提交签退时也没有复核当前开始时间。

```json
{"openOutStatus":200,"postponeStatus":200,"newStartInFuture":true,"signOutBeforeNewStartStatus":200}
```

结果是现场记录对应旧安排，却被用于新的活动时间；已有签到记录还占用原主键，重新开放不等于新场次可重新签到。

建议：明确已有现场记录后的改期政策。可冻结这种修改，或对场次版本化；允许改期时原子失效旧窗口，提交签退时也应重新检查当前时间。不要为了实现重签直接删除历史证据。

## A5 · P2：后续活动改名可绕过跨来源重复学时检查

位置：`server/server.js:814-835`，对比平台确认/审核中的 `evidence.preventDuplicateCredit()`。

同一人的平台活动 A 已认定 2 学时，自行培训 B 在同一天也已认定 2 学时。随后管理员把 A 的标题改成 B，开始时间和学时不变，PUT 会通过。现在两条记录完全同人、同日、同名，但仍合计 4 学时。

```json
{"renameStatus":200,"titles":["活动B","活动B"],"creditedHours":4}
```

这是现有“同人、同日、同名跨来源防重”策略被后续编辑破坏，不是在声称系统能够自动判断语义上是否同一场培训。

建议：活动标题等用于防重的元数据修改时，对已有认定重新检查冲突，冲突应拒绝修改或交人工明确处理，不能静默保留双计，也不能自动抹除既有认定。

## A6 · P2：审核会提交输入框里看不见的旧意见

位置：`pages/reviews/reviews.js:18-27,32-53`、`pages/reviews/reviews.wxml:27-32`。

管理员给 A 输入意见后先审核 B。B 完成后列表被清空、重新加载；在列表实际重建时，A 的意见输入框因未绑定 `value` 显示为空，但 `notes[A]` 仍存在。此时驳回 A，仍会提交旧意见，跳过“请填写驳回原因”的校验。

VM 复现实际 POST 带 `old reason for A`，且记录了列表重建；输入值是否保留取决于原生节点是否重建，网络较慢时尤其应覆盖。

建议：将输入与草稿状态一致绑定，审核完成后清理对应草稿；记录重提/版本变化时避免沿用旧版本意见。前端看见的值必须与提交值一致。

## A7 · P2：关闭签到会删除仍有效的签退二维码

位置：`pages/attendance-manage/attendance-manage.js:44-50`。

先开放签到，再开放签退，当前展示签退二维码；点击签到的“立即关闭”。代码关闭任意 phase 后都会删除当前图像并清空显示，签退窗口却仍有效。

VM 证据：`deleted=["out-code.png"]`，同时 `signOutStillActive=true`。后端只保存哈希，不能重新取回旧二维码；只能刷新签退码，导致正在扫码的旧码失效。

建议：保存当前展示二维码的 phase，只有关闭对应类型时才清除；不同验证窗口的显示状态应独立管理。

## A8 · P2：名单搜索草稿与旧分页游标混用，漏行并混入旧结果

位置：`pages/users/users.js:31-36`。

全名单已经加载前 20 人后，输入“学院B”但尚未点搜索，再点击“加载更多”。输入已直接改 `query`，旧 `nextOffset=20` 却未重置，因此请求学院B的 offset=20，并追加到学院A旧列表。

VM 输出请求 `q=学院B&limit=20&offset=20`；界面仍显示 20 名学院A人员，学院B的第一页被跳过。

建议：区分草稿查询和已应用查询，或输入变化时立即禁用分页、重置游标。统一统计页已有类似隔离机制，可以沿用同一原则。

## A9 · P3：导出中切后台再返回，失败后导出按钮不能自行恢复

位置：`pages/stastic/static.js:28-29,139-145`。

慢网络导出中切后台，再在下载未结束时返回：隐藏会清空 `loadedSignature/canExport`，显示时因 `exporting=true` 跳过加载；最终失败只清 `exporting`，未重新刷新或恢复已加载条件。

VM 合法事件序列结果：`rows=1,canExport=false,errorMessage="",apiCalls=2`。页面还有数据，但不能再次直接导出，缺少持久重试提示；手动查询或重新进页可恢复，因此列 P3。具体手机后台下载时序仍需真机确认。

建议：维护可见性/待刷新状态，导出结束后恢复必要的数据加载，或明确提供恢复按钮。
