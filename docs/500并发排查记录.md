# 500 并发连接排查与验证（2026-11-11）

## 定位与修复

环境：Windows 10.0.26300，Node v26.12.1，libuv 1.52.1，IPv4 loopback，backlog=2048。没有改系统配置、开发数据库或降低 SQLite 持久性；磁盘测试 journal_mode=wal、synchronous=2（FULL）。

旧压测在同一个进程内同时运行 500 个 HTTP 客户端与服务端，而且使用内存库。首轮读请求 232 个 HTTP 200、268 个 ECONNREFUSED（HTTP 响应率 46.4%）；报名阶段也有 36 个连接拒绝。不能将其归因于 SQLite 锁。

`connection-probe.js` 完全移除业务逻辑与 SQLite，仅返回 `ok`：同进程仍是 232 成功、268 拒绝；独立进程为 500 成功。将同进程 backlog 从 2048 增至 2147483647，结果仍是 232/268。这证明当前复现依赖运行方式，而不是报名实现或一个已证明的操作系统“最多 232 连接”限制。客户端突发创建连接时，共用事件循环不能及时运行服务端接入；队列具体由哪个 Windows provider 限制，尚未通过包捕获定位，不能断言注册表参数或防火墙就是原因。

Microsoft Winsock 文档说明：接入队列满时可能产生 WSAECONNREFUSED，backlog 由 provider 限制，传入值不等于实际队列大小：
https://learn.microsoft.com/windows/win32/api/winsock2/nf-winsock2-listen

修复内容：

- 压测改成独立服务进程，由 IPC 在监听完成后通知客户端；默认使用工作区内独立临时磁盘数据库，正常/测试失败退出后清理。保留 `--memory` 便于对照。零重试，15 秒请求总期限，错误计入结果，未达到预期退出码非零。
- 服务端固定 SQL 使用有界 prepared statement 缓存（最多 128 项），避免高并发反复编译。
- 报名的满员、重复、截止预检在写事务外执行，避免确定失败的请求申请 SQLite 写锁；写锁内再检查一次，保留 BEGIN IMMEDIATE、COMMIT/ROLLBACK 及复合主键，防止多进程竞态与超卖。事务内没有 await。
- 提供 LISTEN_BACKLOG 环境变量，默认保持 2048。增加 backlog 本机未解决同进程复现问题，不应当作已验证修复。

SQLite DatabaseSync 仍是同步、单写者：磁盘提交和外部写锁等待会阻塞事件循环，原有 busy_timeout=5000 仍保留。本次没有模拟外部进程长期持锁，不能把本次结果推广为多写者/慢磁盘 SLA，也没有为了吞吐改为 synchronous=OFF/NORMAL。未引入多服务进程争写、自动重试报名或放松数据约束。

## 实测结果

以下每个业务场景各 4 阶段、每阶段 500 次，共 6000 次请求；3 个场景均 HTTP 响应率 100%、预期业务状态符合率 100%，无连接拒绝、超时或 5xx。报名成功率须按容量解释：满额场景 25%（125/500），余下 75% 为预期的 HTTP 409，不是网络失败。不限人数场景报名成功率 100%。

| 场景 | 阶段 | HTTP 状态 | P50 / P95 / P99 / 最大（ms） |
|---|---|---|---|
| 冷连接直接报名，容量125 | 报名 | 200×125，409×375 | 383 / 417 / 420 / 420 |
| 同上 | 活动列表 | 200×500 | 79 / 151 / 156 / 158 |
| 同上 | 再次报名 | 409×500 | 44 / 62 / 64 / 65 |
| 同上 | 年度统计 | 200×500 | 68 / 140 / 147 / 148 |
| 冷连接直接报名，不限人数 | 报名（500次实际写入） | 200×500 | 582 / 985 / 1022 / 1032 |
| 同上 | 活动列表 | 200×500 | 136 / 235 / 243 / 245 |
| 同上 | 重复报名 | 409×500 | 87 / 178 / 185 / 186 |
| 同上 | 年度统计 | 200×500 | 142 / 277 / 287 / 288 |
| 500 预连接，容量125 | 活动列表 | 200×500 | 119 / 208 / 213 / 215 |
| 同上 | 报名 | 200×125，409×375 | 261 / 294 / 297 / 301 |
| 同上 | 再次报名 | 409×500 | 54 / 78 / 80 / 80 |
| 同上 | 年度统计 | 200×500 | 112 / 200 / 208 / 210 |

每个场景服务端接受 500 个连接，处理 2000 个请求；只有第一阶段建立冷连接，其余阶段复用连接。`--register-first` 确保首轮直接压报名，不以预热读取掩盖接入与写入同时发生。并发指同时发起 500 次请求，并非数据库同时执行 500 个写事务。

落库分别为 125、500、125 条；重复键分组为 0，foreign_key_check 为空，integrity_check=ok。满员后的再次报名保持总数不变。原始 JSONL 见 `load-results/`。`npm test` 的 8 个测试组全部通过。本结果是本机小数据集单轮观测，不包含真实网络、HTTPS 代理或持续压力。

## 可执行复现和环境调整

在项目的 server 目录执行（无需启动开发服务）：

```powershell
npm test
npm run test:load
npm run test:load:cold
node load-test.js --cold --register-first
npm run test:load:writes
node connection-probe.js --same-process # 本机预期非零退出，复现拒绝
npm run test:connections               # 独立进程对照
```

当前已验证有效的环境调整是把负载发生器与服务端分开进程；更新后的负载命令自动完成，普通 `node server.js` 本身就是独立服务进程。没有证据要求修改 Windows 注册表、关闭防火墙、扩大端口范围或增加 UV_THREADPOOL_SIZE（它不解决同步 SQLite）。

目标环境若仍有连接拒绝，先确认监听与绑定地址，再分别跑纯 HTTP 对照和业务负载：

```powershell
Get-NetTCPConnection -LocalPort 3000 -State Listen
$env:LISTEN_BACKLOG = '8192'
node server.js
# 另一个终端/独立机器发起负载；本仓库测试启动独立临时端口服务，不测试上面3000端口
# 完成对照后在原终端 Ctrl+C，再恢复环境变量
Remove-Item Env:LISTEN_BACKLOG
```

本机已证明增大队列并非必需或有效修复；正式部署若经过代理，需另测真实 HTTPS 地址并检查代理连接数/日志和服务端监听队列。当前没有目标 Linux 服务器，不能报告 Linux 内核限制已验证。若迁移 Linux，先查询 `sysctl net.core.somaxconn net.ipv4.tcp_max_syn_backlog`、`ulimit -n` 和 `ss -lnt`，仅在确认队列/文件描述符不足后调整系统与服务管理器限制，并重新跑同样负载。正式学校环境仍需独立验收。
